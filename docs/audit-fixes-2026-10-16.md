## التحقق

- اختبارات الخادم: **56/56**، دون اختبارات متخطاة عند توفير اتصال اختبار SQL Server.
- اختبارات المتصفح: **18 اختباراً**: سبعة للطباعة وأحد عشر لسلوك النظام، تشمل استعادة الدفع والإيداع بعد إعادة التحميل، وتصدير فترة صحيحة، والإلغاء، وإدارة المستخدمين، والتخصيص، والتواريخ.
- `npm run lint`: ناجح دون أخطاء أو تحذيرات.
- `npm run build`: ناجح. يبقى تحذير Vite عن حجم الحزمة الرئيسية؛ لا يمنع البناء، ولم تُعطل عتبة التحذير.
- `npm audit --json`: صفر تنبيهات، بما فيها اعتماديات التطوير.
- فحص NuGet للاعتماديات المباشرة والانتقالية: لا توجد حزمة مبلغ عنها في النتيجة المكتملة.
- نموذج EF متوافق مع آخر migration؛ لا توجد تغييرات نموذج غير مرحّلة.
- SQL Server الفعلي: ترقية بيانات سابقة وتهيئة جديدة، وتوزيع سنت الخصم، وترجمة التقارير، ودفع متزامن، ومنع سحب فوق الرصيد، وإغلاق متزامن، وتوازن الدرج، ومنع الحذف المتسلسل، والرجوع عن الترحيلات مع حفظ الاسترداد. أُنشئت قواعد اختبار مستقلة وحُذفت بعد التحقق؛ لم تُستخدم قاعدة المطعم.

لتكرار الفحص من جذر المستودع:

```powershell
# الاتصال يجب أن يكون بخادم اختبار يسمح بإنشاء قواعد مؤقتة؛ لا يحدد اسم قاعدة المطعم.
$env:RESTAURANT_TEST_SQLSERVER = 'Server=(local);Integrated Security=true;TrustServerCertificate=true'
dotnet test Restaurant.Services.Tests/Restaurant.Services.Tests.csproj
```

اختبار SQL Server ينشئ أسماء عشوائية تبدأ بـ`RestaurantAuditFixes_`، ويتحقق من أسمائها قبل حذف قواعد الاختبار في finally. عند عدم تحديد المتغير يُتخطى اختبار التكامل وحده مع ذكر السبب؛ بقية الاختبارات تعمل على SQLite في الذاكرة.

للمتصفح: شغّل Vite محلياً على `127.0.0.1:5193` ثم `npm run test:browser` داخل `restaurant.web`. يستخدم Edge افتراضياً، ويمكن تحديد المتصفح عبر `PRINT_TEST_BROWSER` ورابط الواجهة عبر `RESTAURANT_TEST_URL`. لا تُرسل الاختبارات أعمالاً لطابعة فعلية.

## تشغيل الإصلاحات على بيانات المطعم

الترحيل الجديد هو [ProtectAccountingAndAuthorization](C:/Users/Masoud/source/repos/Restaurant.API/Restaurant.DataAccess/Migrations/20261015222254_ProtectAccountingAndAuthorization.cs). لم يُطبّق على قاعدة المطعم أثناء هذه المهمة. يلزم نشر الخادم والويب معاً؛ إعداد Seeder الحالي يطبق الترحيلات عند إقلاع API.

قبل تحديث قاعدة تشغيلية، احتفظ بنسخة قابلة للاستعادة. الترحيل يضيف حقولاً وفهارس ويملأ اللقطات وخصم البنود من البيانات المتاحة، ولا يعيد كتابة مبالغ القيود المالية. البيانات التاريخية التي لم تكن محفوظة أصلاً لا يمكن استعادتها بدقة: اللقطات القديمة تُملأ بأسماء الكتالوج المتاحة وقت الترحيل، ووقت الإلغاء القديم يُستنتج من أول استرداد أو تاريخ الطلب.

مدفوعات البطاقة القديمة التي سُجلت سابقاً خطأ كنقد قد تكون أثرت في مطابقة ورديات مغلقة. لم تُعد كتابة هذه القيود والإغلاقات آلياً؛ يلزم مراجعة الرصيد وتسوية أي فرق موجود وفق السجل الفعلي. التصنيف المصحح يُستخدم للمدفوعات الجديدة.

الرموز القديمة التي لا تحمل SecurityStamp ستُرفض بعد تحديث API؛ يحتاج المستخدمون إلى تسجيل الدخول مجدداً. إعداد الخادم `Business:TimeZone` وإعداد الويب `VITE_BUSINESS_TIME_ZONE` افتراضهما Africa/Tripoli، ويجب أن يتطابقا عند تغييره.

مسارات القوائم القديمة تظل تعيد مصفوفات لكنها أصبحت محدودة الصفحة. تستخدم واجهة الويب مسارات `paged` وعداد السجلات؛ أي عميل آخر يعتمد تحميل السجل كله بطلب واحد يحتاج استعمال الصفحات.
