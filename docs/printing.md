# الطباعة واسم المطعم

## ربط واجهة الويب بخدمة PrintService

واجهة `restaurant.web` تستخدم خدمة الطباعة المحلية افتراضياً للفواتير والمطبخ والتقارير. يتصل المتصفح بالخدمة على جهاز الكاشير مباشرة؛ لا يمر الطلب بخادم Restaurant.API، ولا يُرسل رمز تسجيل الدخول إلى وكيل الطباعة. تكامل سطح المكتب الحالي عبر WPF مستقل عن هذا الربط.

1. شغّل الوكيل على جهاز الطابعات:

   ```powershell
   dotnet run --project C:\Users\Masoud\source\repos\PrintService\PrintService.Host --no-launch-profile -- --Printing:DocumentEngine=Win32Gdi
   ```

2. افتح **الإعدادات ← الطابعات والأجهزة** ثم **حفظ العنوان وفحص الاتصال**. العنوان الافتراضي `http://127.0.0.1:5055`. اسمح بالوصول للشبكة المحلية إذا طلب المتصفح ذلك.
3. أضف الطابعات بأسماء تعريفات Windows المطابقة للقائمة المقترحة. لكل طابعة نوع: فاتورة، مطبخ أو تقرير، ومحطة مرتبطة. اختبار الطباعة يرسل صفحة اختبار إلى الطابعة المحددة عبر الخدمة.
4. اربط التصنيفات بمحطات الطباعة من إعدادات التصنيفات. تستخدم تذاكر المطبخ `categoryId` المحفوظ في عنصر الطلب، وترسل لكل محطة أصنافها فقط. غياب الربط أو طابعة المحطة يظهر خطأ قبل إرسال أي تذكرة في تلك المحاولة. تُرسل الفاتورة إلى طابعات الفواتير المعرفة والتقارير إلى طابعات التقارير.
5. اختر ورق الفواتير والمطبخ لكل طابعة على هذا الجهاز: **80 مم** (الافتراضي)، **58 مم** أو **A4**. تستخدم `Microsoft Print to PDF` ورق A4 افتراضياً، لأن تعريفها قد يرفض مقاساً حرارياً مخصصاً. يجب أن يقبل تعريف الطابعة الأبعاد المرسلة؛ تعرض الواجهة رسالة الخدمة إذا رفضها. التقارير تستخدم A4 دائماً.

تحوّل الواجهة القوالب إلى PNG بدقة مضاعفة للحفاظ على تشكيل العربية والجداول، ثم ترسل `documentType: 4` مع `systemId` ومعرّف مهمة فريد وخيارات الصفحة. لا يتطلب هذا المسار SumatraPDF. تُقسّم المستندات الطويلة إلى صفحات مع تفضيل حدود صفوف الجدول. نجاح الإرسال يعني قبول المهمة في مخزن Windows، وليس تأكيد خروج الورق.

أُجري اختبار فعلي من Edge إلى الوكيل ثم `Microsoft Print to PDF` ونتج ملف PDF مع الحالة `Submitted` باستخدام `Win32Gdi`. محرك `PrintDocument` الافتراضي للخدمة لم يؤكد ملف الإخراج على هذا الجهاز؛ لذلك يحدد أمر التشغيل أعلاه المحرك البديل دون تغيير إعدادات مشروع PrintService. ما زال اختبار الطابعة الحرارية الفعلية مطلوباً عند توفرها.

يحفظ IndexedDB محتوى المحاولة ومعرّفاتها قبل الإرسال. عند فقد الرد أو تحديث الصفحة، يعيد زر الطباعة نفسه متابعة المحتوى والمعرّفات المحفوظة؛ يتعرف الوكيل عليها ولا يعيد إرسالها. تحتفظ المحاولة الناجحة جزئياً بوجهاتها المؤكدة وتتجاوزها عند المتابعة. بعد تأكيد كل الوجهات، تُحذف المتابعة وتصبح إعادة الطباعة التالية نسخة جديدة بمعرّفات جديدة. الفاتورة والمطبخ محاولتان منفصلتان؛ عند فشل إحداهما أعد طباعة النوع الذي فشل فقط.

تعرض الإعدادات المحاولات غير المؤكدة وتتيح الاستعلام عن حالتها عبر `/api/jobs/{jobId}`. حالة `Unknown` تتطلب التحقق من مخزن Windows أو الورق قبل إنهاء متابعة المحاولة والسماح بنسخة جديدة. إذا فشلت المحاولة كلها قبل الإرسال، تُجهّز المحاولة التالية من الإعدادات المصححة. لا تُعاد المهام تلقائياً عند عودة الاتصال، ولا يُحذف الطلب أو يُعاد البيع بسبب خطأ طباعة.

العنوان وطريقة الطباعة ومقاس كل طابعة محفوظة لهذا المتصفح. يمكن اختيار **نافذة طباعة المتصفح** أو استخدام **فتح صفحة الطباعة** عند الحاجة. يمكن ضبط قيم البناء عبر `.env.local` بالاعتماد على `restaurant.web/.env.example`: `VITE_PRINT_SERVICE_URL` و`VITE_PRINT_SYSTEM_ID`. لا يلزم ترحيل قاعدة بيانات لهذا الربط.

للتحقق الآلي شغّل Vite على 5193 ثم نفّذ `node --test --test-concurrency=1 tests/*.browser.test.cjs` داخل `restaurant.web`. اختبارات `print-agent.browser.test.cjs` تحاكي الوكيل، وتتحقق من الصور، وتوجيه المحطات، واستعادة نفس المعرف والمحتوى بعد انقطاع الاتصال أو تحديث الصفحة، واستكمال الوجهات المتبقية، وصفحات A4 وإعدادات الأجهزة؛ لا ترسل إلى طابعة فعلية.

## اسم المطعم

- يستخدم الويب وسطح المكتب `GET /api/restaurants/current` لقراءة المطعم المرتبط بالمستخدم من قاعدة البيانات، دون الاعتماد على بيانات تسجيل دخول قديمة.
- المستخدم القديم غير المرتبط بمطعم يحصل على المطعم الوحيد إذا كان هناك مطعم واحد. عند وجود عدة مطاعم يجب ضبط الارتباط؛ لا يختار النظام اسماً عشوائياً.
- الفواتير ومعاينتها والتقارير وملفات CSV تستخدم الاسم المحفوظ في إعدادات المطعم. تحديثه في الإعدادات يحدّث الاسم المعروض أيضاً.
- تعذر قراءة الاسم يمنع طباعة فاتورة باسم افتراضي غير صحيح ويعرض سبب الفشل.
- تعديل الشيفرة يتطلب إعادة تشغيل الـAPI وتحديث صفحة الويب. لا يتطلب هذا الإصلاح ترحيلاً جديداً لقاعدة البيانات.

## Edge وdoPDF 11

تنتظر طلبات الطباعة بعضها بعضاً. يبقى المستند حتى حدث `afterprint` أو انتهاء وضع الطباعة، ولا يُحذف بعد مؤقت قصير أثناء اختيار الطابعة. تستخدم الفواتير حجم الورق الذي تختاره الطابعة، والتقارير ورق A4.

إذا ظهر خطأ داخل `edge://print` أثناء تحميل قدرات doPDF، استخدم «فتح صفحة الطباعة» من معاينة الفاتورة أو صفحة التقارير. في الصفحة الجديدة اضغط **Ctrl+Shift+P** لفتح نافذة طباعة Windows، ثم اختر **doPDF 11**. يمكن لصفحة ويب تجهيز المستند وفتح الطباعة، لكنها لا تستطيع اختيار طابعة Windows أو إصلاح شيفرة معاينة Edge الداخلية مباشرة.

المراجع الرسمية: [اختصارات Microsoft Edge](https://support.microsoft.com/en-us/edge/keyboard-shortcuts-in-microsoft-edge)، [تشخيص مشاكل الطباعة في Edge](https://support.microsoft.com/en-us/edge/troubleshoot-print-issues-in-microsoft-edge).

## التحقق

- اختبارات الخدمات وHTTP: `dotnet test Restaurant.Services.Tests/Restaurant.Services.Tests.csproj`.
- بناء الويب: `npm run build` داخل `restaurant.web`.
- اختبارات المتصفح: شغّل Vite على المنفذ 5193، ثم `node --test tests/printing.browser.test.cjs` داخل `restaurant.web`. يتطلب Playwright وEdge؛ يمكن تحديد مكتبة Playwright المرفقة عبر `PLAYWRIGHT_MODULE_PATH`، أو تغيير المتصفح عبر `PRINT_TEST_BROWSER`.
- هذه الاختبارات تستبدل طلبات الـAPI وتستدعي أحداث نهاية الطباعة للتحقق من ترتيب المستندات وبقائها. تختبر كذلك الاسم الحقيقي في المعاينة والفاتورة والتقرير وتصدير CSV، وتوليد PDF باستخدام محرك Edge. لا تُرسل مهمة إلى طابعة الجهاز ولا تختبر نافذة doPDF الأصلية.

إذا كانت جلسة Visual Studio تحجز ملفات الـAPI، استخدم `--artifacts-path Restaurant.Services.Tests/obj/printing-verification` مع أمر الاختبارات لبناء نسخة معزولة.
